Tried 4 different PDF-to-Markdown libs:
1. pymupdf4llm
Headings detected correctly (font-size heuristic),
SQL/code blocks kept syntactically correct (operators intact), fenced most of the time
(occasionally splits one statement across 2-3 fences at layout-box boundaries).
Only real weakness: tables and images. Image text is captuired in block but unusable.

2.pdfoxide
Strips operators (=, -, >) from every SQL/code block (e.g. "WHERE concert_id = 'x'" comes out as "WHERE concert_id  'x'"), 
Also no code fences at all (comments and SQL get mashed into plain prose). Tables have missing cell content gets dumped as incoherent orphaned paragraphs.
Link text fragments into multiple adjacent links.

3.pdf-inspector
Fastest overall (Rust/PyO3), and unlike pdf-oxide it keeps SQL operators intact
But zero code fences appear nywhere in the output despite docs claiming monospace-font-based code-block detection.
Same as pymupdf4llm's text quality but with no code-block signal.

4. docling
Preserves real hyperlinks as markdown links.
do_code_enrichment and generate_picture_images are deliberately left off -
both add real latency (a second model load + per-region inference)
Code comes through as CodeItem.text un-reflowed (flattened
single-line, same as the raw layout-model output); pictures fall back to
a plain <!-- image --> placeholder since there's no cropped image data to
generate a caption from. Table for the most part is correct, maybe fail with no borders.

[pymupdf4llm] took 3.0385 seconds on data/dealing-with-contentions.pdf
[docling with ocr] took 208.7649 seconds with auto accelerator device
[docling_no_ocr] took 37.5378 seconds with auto accelerator device
[docling_no_ocr] took ~98 seconds with CPU accelerator device
[pdf-oxide] took 0.2575 seconds
[pdf-inspector] took 0.1030 seconds

pymupdf was a fast choice but it produces poor conversion especially with tables. Table cell text are broken across multiple rows. Pictures are captured but with gibberish descriptions. It's also super fast.
That said, we went with docling because it captured tables and code blocks with more stability; however, it's a bit slower since it has to load PyTorch transformers.
But what we gain are correct table layouts and code blocks though code blocks can be separated, but that's due to the corpus. Our tables are not complex either so might be sth to check for complex table configs.
We turned off OCR too since we have already layered text, also improved the latency too.
Docling has support for picture caption generation and code enrichment but those would require more transformers to load which makes it super slow. Disable those.
Roughly 10 mins for data/dealing-with-contentions.pdf with them on. 
Alternatively, docling has a VLM pipeline that we can use to parse the PDF which captures the text formatting on top of the table and code blocks. But still doesn't capture pictures.
Since our corpus has a lot of diagrams that are useful for answering questions, we should describe pictures instead of removing them so we decide to use a hybrid solution. 

1. We don't use docling `export_to_markdown` since it renders a poor markdown with stray diagram labels, separate code blocks that were originally one, broken paragraphs. We write our render function that has all those logic baked in. 
2. With our custom render function, we also can integrate VLM enrichment for pictures and LLM-based table summarization. 

We decide to do this to improve chunking and make sure the data is as clean as we can get before we chunk and index it.
